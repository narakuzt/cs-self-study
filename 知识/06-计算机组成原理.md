## 概念清单

学完主题 6 后，下面每一条都应能用一两句话解释并举出例子。括号里是对应的题目。

### 数据的位宽与表示

- 不同整数类型占的字节数由平台决定，64 位系统上 `int` 常是 4 字节、`long` 常是 8 字节（Q06-01）
- 无符号数溢出是良性的环绕（回到 0），有符号数溢出是未定义行为（Q06-02、Q06-03）
- 浮点数按 IEEE 754 标准存储：符号位、指数位、尾数位（Q06-04）
- 特殊浮点值：正负无穷、NaN、正负零（Q06-05）

### 字节序

- 大端把高位字节放在低地址，小端把低位字节放在低地址；x86-64 是小端（Q06-06）

### 汇编与调用约定

- 高级语言的每条语句最终对应若干条机器指令（汇编是机器指令的可读形式）（Q06-07）
- x86-64 常见调用约定：前几个整数参数通过寄存器传递，不是都压栈（Q06-08）
- 函数调用会保存返回地址，形成调用栈；递归过深会耗尽栈空间（Q06-09、Q06-10）

### 存储层次（衔接主题 1）

- 局部性原理：程序倾向于反复访问最近用过的数据（时间局部性）和相邻的数据（空间局部性），这是缓存有效的前提（Q06-11）
- 缓存命中与缺失；缺失时要去下一级存储取数据，更慢（Q06-12）

### 指令集与体系结构

- CISC（复杂指令集）与 RISC（精简指令集）的基本区别（Q06-13）
- 冯·诺依曼结构里，指令和数据走同一条总线，可能成为瓶颈（Q06-14）

### 用工具观察硬件层面

- 用 `gdb` 查看寄存器的值（Q06-15）
- 编译产物的大小和内容与优化级别有关（Q06-16）

## 自测题库

### Q06-01 不同整数类型的位宽

- 类型：代码题
- 出处：C 标准对整数类型宽度的规定是"平台相关的最小保证"，具体值由编译器和平台决定
- 问题：在你的机器上，`char`、`int`、`long`、指针各占几个字节？

```c
#include <stdio.h>
int main(void) {
    printf("%zu %zu %zu %zu\n", sizeof(char), sizeof(int), sizeof(long), sizeof(void *));
    return 0;
}
```

- 答案：

```text
1 4 8 8
```

C 标准只保证 `char` 至少 1 字节、`int` 至少 16 位、`long` 至少 32 位，并保证 `char ≤ short ≤ int ≤ long ≤ long long`，具体是多少字节由平台的 ABI（应用二进制接口）决定。在常见的 64 位 Linux 系统上，`int` 是 4 字节、`long` 和指针都是 8 字节；这与主题 3 Q03-04 里"64 位系统上指针占 8 字节"是同一个结论。

### Q06-02 无符号数溢出是良性环绕

- 类型：代码题
- 出处：C 标准规定无符号整数运算按 2 的位宽次方取模，不会溢出
- 问题：`unsigned int` 的最大值再加 1 会怎样？

```c
#include <stdio.h>
#include <limits.h>
int main(void) {
    unsigned int x = UINT_MAX;
    printf("%u %u\n", x, x + 1);
    return 0;
}
```

- 答案：

```text
4294967295 0
```

标准明确规定，无符号整数运算的结果按 2 的位宽次方取模，超出范围时"环绕"回来，这是良性定义好的行为：`UINT_MAX`（32 位时是 2³²-1）加 1，结果模 2³² 等于 0。这条规则也是主题 1 Q01-05"固定位宽下的溢出"的标准依据。

### Q06-03 有符号数溢出是未定义行为

- 类型：概念题
- 出处：C 标准规定有符号整数溢出是未定义行为（这一点与无符号数不同）
- 问题：`INT_MAX + 1` 和 `UINT_MAX + 1` 在标准里的地位一样吗？
- 答案：

不一样。`UINT_MAX + 1`（Q06-02）是标准明确定义的行为：结果按 2 的位宽次方取模。但 `INT_MAX + 1`（有符号整数溢出）是**未定义行为**：标准不保证任何具体结果，编译器可以假设它永远不会发生，并据此做激进的优化——这意味着实际运行结果可能是环绕、可能是别的数、程序也可能被优化成看起来不合逻辑的样子。这也是为什么涉及可能溢出的计算，应当优先用无符号类型或提前检查边界，而不能依赖"有符号溢出反正也是环绕"这种在其他平台不成立的假设。

### Q06-04 IEEE 754 浮点数的位结构

- 类型：代码题
- 出处：IEEE 754 二进制浮点数标准（单精度 32 位：1 位符号、8 位指数、23 位尾数）
- 问题：`-6.5` 按 32 位浮点数存储，符号位、指数位、尾数位分别是什么？

```python
import struct

bits = int.from_bytes(struct.pack(">f", -6.5), "big")
sign = bits >> 31
exponent = (bits >> 23) & 0xFF
mantissa = bits & 0x7FFFFF
print(sign, exponent, mantissa)
```

- 答案：

```text
1 129 5242880
```

IEEE 754 单精度浮点数用 32 位表示：最高 1 位是符号位（1 表示负数），接下来 8 位是指数（存的是"真实指数 + 127"的偏移值），剩下 23 位是尾数。`-6.5` 是负数所以符号位为 1；`6.5 = 1.625 × 2²`，真实指数是 2，加上偏移 127 得到 129；尾数部分存的是 `1.625` 去掉最高位的 1 之后按比例映射到 23 位的结果。这也是为什么浮点数不能精确表示所有小数（主题 1 Q01-08）：尾数位数有限。

### Q06-05 特殊浮点值

- 类型：代码题
- 出处：IEEE 754 标准定义的特殊值：无穷、NaN、正负零
- 问题：正无穷、负无穷、NaN 的位模式有什么特征？

```python
import struct

for v in (float("inf"), float("-inf"), float("nan"), -0.0):
    print(v, struct.pack(">f", v).hex())
```

- 答案：

```text
inf 7f800000
-inf ff800000
nan 7fc00000
-0.0 80000000
```

IEEE 754 用指数位全 1 表示特殊值：尾数为 0 时是无穷（符号位区分正负），尾数非 0 时是 NaN（不是一个数，比如 0/0 或 无穷-无穷 的结果）。零也分正零和负零，位模式只有符号位不同，但数值上 `0.0 == -0.0` 为真——浮点数不是"每个位模式对应一个唯一可比较大小的数"这么简单的模型，这些特殊情形是很多浮点相关 bug 的来源。

### Q06-06 字节序

- 类型：代码题
- 出处：字节序（endianness）的定义
- 问题：在内存里，一个多字节整数的最低有效字节存在低地址还是高地址？

```c
#include <stdio.h>
int main(void) {
    unsigned int x = 1;
    unsigned char *p = (unsigned char *)&x;
    printf("%d\n", p[0]);
    return 0;
}
```

- 答案：

```text
1
```

把 `x=1` 的地址当作字节数组来看，如果最低地址那个字节就是 1（也就是数值上"最不重要"的那个字节），说明这台机器是**小端**（little-endian）：低位字节存在低地址。x86-64（几乎所有个人电脑和大多数服务器）都是小端；网络协议（比如 TCP/IP 的包头）则约定使用大端，这也是"网络字节序"这个说法的由来，两者之间需要转换。

### Q06-07 高级语句对应多条机器指令

- 类型：代码题
- 出处：编译器把 C 代码翻译成汇编的例子
- 问题：一句简单的加法 `return a + b;`，编译后大致对应哪些操作？

```bash
cat > add.c <<'C'
int add(int a, int b){ return a + b; }
C
gcc -S -O0 -o - add.c | grep -cE '^\s*(movl|addl|ret)'
```

- 答案：

```text
6
```

一句 C 语句在编译后展开成若干条更底层的操作：把两个参数从寄存器挪到栈上保存（2 条 `movl`）、再取出两个操作数到寄存器（2 条 `movl`）、做加法（`addl`）、把结果放进约定的返回寄存器并返回（`ret`），一共 6 条。具体条数和写法会随编译器版本、优化级别变化（开优化后可能只剩一两条指令），这里只统计几类关键指令的出现次数，不依赖某个具体版本的确切输出。

### Q06-08 调用约定：参数通过寄存器传递

- 类型：代码题
- 出处：x86-64 System V ABI（Linux/macOS 上的调用约定，规定前几个整数参数依次用 edi、esi、edx… 等寄存器传递）
- 问题：调用一个两参数的函数，参数是直接压栈，还是放进寄存器？

```bash
cat > call.c <<'C'
int add(int a, int b){ return a + b; }
int main(void){ return add(3, 4); }
C
gcc -S -O0 -o - call.c | grep -cE 'edi|esi'
```

- 答案：

```text
4
```

x86-64 的 System V 调用约定规定：前 6 个整数或指针参数依次通过 `edi`、`esi`、`edx`、`ecx`、`r8d`、`r9d` 这些寄存器传递，只有超过 6 个或者是浮点数等特殊类型才会用到栈。这里 `add` 函数把两个参数从 `edi`、`esi` 存到栈上局部变量（2 次），`main` 里调用前把常量 3、4 分别放进 `edi`、`esi`（2 次），一共 4 次涉及这两个寄存器。这和很多人以为的"所有参数都要压栈"不同，也是为什么函数调用的开销比想象中小。

### Q06-09 函数调用形成调用栈

- 类型：代码题
- 出处：函数调用栈（call stack）的基本模型
- 问题：函数嵌套调用时，"返回地址"是怎么被记住的？

```c
#include <stdio.h>
int depth = 0;
void recurse(int n) {
    depth++;
    if (n > 0) {
        recurse(n - 1);
    }
}
int main(void) {
    recurse(5);
    printf("%d\n", depth);
    return 0;
}
```

- 答案：

```text
6
```

每次函数调用，CPU 会把"调用之后应该回到哪里继续执行"（返回地址）连同函数的局部变量、参数一起压入调用栈，形成一个"栈帧"；函数返回时弹出栈帧，取出返回地址继续执行。这样多层嵌套调用才能正确地一层层返回。这里 `recurse(5)` 连同最初的调用共执行了 6 次（n=5,4,3,2,1,0），对应调用栈曾经深达 6 层。

### Q06-10 递归过深耗尽栈空间

- 类型：代码题
- 出处：调用栈空间有限，是"栈溢出"（stack overflow）名称的由来
- 问题：如果递归没有终止条件（或者层数远超栈能容纳的深度），会怎样？

```python
import sys

sys.setrecursionlimit(200)

def f(n):
    return f(n + 1)

try:
    f(0)
except RecursionError:
    print("RecursionError")
```

- 答案：

```text
RecursionError
```

每次函数调用都要占用一份调用栈的空间（Q06-09），而调用栈的总空间是有限的。在 C 这类语言里，无限递归（或递归层数远超预期）最终会耗尽栈空间，触发段错误，这正是"栈溢出"这个术语的原始含义（和网站 Stack Overflow 同名，但概念上是这个意思）。Python 出于安全考虑设置了一个递归深度限制（可以用 `sys.setrecursionlimit` 调整），超过时会抛出可以捕获的 `RecursionError`，而不是让程序直接崩溃。

### Q06-11 局部性原理

- 类型：概念题
- 出处：存储层次有效工作的理论基础
- 问题：为什么缓存这种"小而快"的存储能大幅提升性能，而不需要把所有内存都做得那么快？
- 答案：

这依赖"局部性原理"里的两条经验规律：**时间局部性**——最近被访问过的数据，很可能在不久之后再次被访问（比如循环体里反复用到的变量）；**空间局部性**——被访问的数据，它附近的数据也很可能很快被访问到（比如遍历数组时，访问了 `a[i]` 之后紧接着会访问 `a[i+1]`）。缓存正是利用这两条规律：把最近用过、以及它附近的数据整块搬到快速的缓存里，之后的访问大概率能直接命中缓存，不用每次都去慢得多的主存取。这也解释了为什么"按行遍历二维数组"通常比"按列遍历"快得多——按行访问时，相邻元素在内存里也是相邻的，能更充分利用空间局部性；这个差异是真实存在的，但具体快多少取决于硬件和数据规模，因此不适合作为一道要求精确计时的题目。

### Q06-12 缓存命中与缺失

- 类型：概念题
- 出处：缓存的基本工作方式
- 问题：什么是缓存命中？什么是缓存缺失？缺失之后会怎样？
- 答案：

CPU 要读一块数据时，先看它是否已经在缓存里：如果在，叫**命中**（hit），可以很快拿到；如果不在，叫**缺失**（miss），必须去下一级更慢的存储（可能是更大一级的缓存，最终是主存）里取，取到之后通常还会顺便把这块数据（连同附近的数据，按 Q06-11 的空间局部性）放进缓存，方便下次命中。程序如果访问模式杂乱无章（比如随机跳着访问一大片内存），缓存命中率会很低，性能会明显不如访问模式规整、局部性好的程序，即使两者做的"逻辑工作量"是一样的。

### Q06-13 CISC 与 RISC

- 类型：概念题
- 出处：两类指令集设计哲学的经典区分
- 问题：CISC 和 RISC 分别是什么意思？
- 答案：

CISC（Complex Instruction Set Computer，复杂指令集）追求用少数几条功能强大、复杂的指令完成很多工作，一条指令可能包含多个步骤（比如直接从内存读取、运算、再写回内存），x86 系列是典型代表。RISC（Reduced Instruction Set Computer，精简指令集）追求用大量简单、执行时间统一的指令组合出复杂功能，通常严格区分"访存指令"和"运算指令"（运算只能在寄存器间进行），ARM、RISC-V 是典型代表。这不是谁绝对更好的问题，而是不同的设计取舍：RISC 的指令更容易做流水线优化，CISC 在某些场景下代码更紧凑。现代 x86 处理器内部实际上会把复杂的 CISC 指令拆解成类似 RISC 的微指令来执行，两者的界限在实现层面已经没那么分明。

### Q06-14 冯·诺依曼瓶颈

- 类型：概念题
- 出处：冯·诺依曼结构的固有限制（与主题 1 Q01-25"程序和数据都在内存里"相衔接）
- 问题：指令和数据共用同一条总线，会带来什么限制？
- 答案：

冯·诺依曼结构下，CPU 从内存取指令、从内存读写数据，走的是同一条总线，同一时刻只能做其中一件事。当 CPU 的运算速度远超总线传输数据的速度时，CPU 常常要等着数据或指令从内存搬过来，这个限制被称为"冯·诺依曼瓶颈"。存储层次（Q06-11、Q06-12）正是缓解这个问题的手段之一：让大多数访问命中更快的缓存，减少真正要走总线去访问主存的次数。也有一些体系结构（如哈佛结构）把指令和数据分成两条独立的总线来缓解这个瓶颈，常见于对实时性要求高的嵌入式芯片。

### Q06-15 用 gdb 查看寄存器

- 类型：代码题
- 出处：GDB 用户手册（`info registers` 命令）
- 问题：怎样在调试时直接看到 CPU 寄存器里的值？

```bash
cat > regs.c <<'C'
int main(void) {
    int x = 12345;
    return x;
}
C
gcc -g -O0 regs.c -o regs
gdb -q -batch -ex 'break 3' -ex run -ex 'print x' ./regs 2>&1 | grep -c '\$1 = 12345'
```

- 答案：

```text
1
```

`break 3` 在第 3 行（`return x;`）设置断点，`run` 让程序跑到断点处暂停，这时可以用 `print 变量名` 直接查看变量当时的值（本质上是读取它所在的寄存器或栈内存）。用 `info registers` 能看到所有通用寄存器当前的值，这比在代码里到处加 `printf` 更直接，也不需要重新编译。

### Q06-16 优化级别影响编译产物

- 类型：代码题
- 出处：GCC 优化选项的基本效果
- 问题：加上 `-O2` 优化，同一段代码编译出的指令数量会怎样变化？

```bash
cat > opt.c <<'C'
int square(int x){ return x * x; }
int main(void){ return square(5); }
C
n0=$(gcc -S -O0 -o - opt.c | grep -c '^\s*\(movl\|imull\|ret\)')
n2=$(gcc -S -O2 -o - opt.c | grep -c '^\s*\(movl\|imull\|ret\)')
[ "$n2" -le "$n0" ] && echo "优化后指令数不增加"
```

- 答案：

```text
优化后指令数不增加
```

`-O0`（默认，不优化）会逐字翻译代码，保留很多为了方便调试而做的中间步骤（比如把参数存到栈上再取出来）；`-O2` 这类优化选项会做常量折叠、内联、去掉多余的读写内存等变换，往往能大幅减少最终的指令数量、提升运行速度，但也让生成的汇编更难对应回原始源码，调试体验变差。这也是为什么开发调试阶段常用 `-O0`，正式发布时才开优化。
