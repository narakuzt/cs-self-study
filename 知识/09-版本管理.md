## 概念清单

学完主题 9 后，下面每一条都应能用一两句话解释并举出例子。括号里是对应的题目。

### 基本模型

- 工作区、暂存区、仓库三个区域，以及 `add`、`commit` 怎样把改动从一个区域移到下一个（Q09-01、Q09-02）
- `status`、`diff`、`log` 怎样查看三个区域之间的差异（Q09-03、Q09-04）
- 提交对象记录一次快照、一段信息、作者与时间，并指向上一个提交（Q09-19、Q09-20）

### 分支与合并

- 分支只是指向某个提交的一个指针，`HEAD` 指向当前分支（Q09-08、Q09-09）
- 新建、切换、合并分支（Q09-08、Q09-10）
- 能快进的合并与需要产生新提交的合并（Q09-10、Q09-11）
- 合并冲突：Git 无法自动决定用哪一边时，需要人工解决（Q09-12）
- 变基与合并达到相似效果，但历史形状不同；变基的适用边界（Q09-13、Q09-14）

### 撤销与找回

- `restore`（撤销工作区改动）、`reset`（回退到某个提交）、`revert`（用一次新提交抵消之前的提交）的区别（Q09-15、Q09-16、Q09-17）
- `reflog` 能找回"丢失"的提交，因为提交对象本身没有立即被删除（Q09-18）

### 远程协作

- `clone`、`remote -v`、`fetch` 与 `pull` 的区别、`push`（Q09-21、Q09-22、Q09-23）
- 忽略文件与 `.gitignore` 的写法（Q09-05）
- 提交信息的写法：标题与正文分开、限制标题长度、用祈使语气（Q09-06、Q09-07）

### 出错与安全

- 提交信息写错、提交漏了文件、需要临时切走但工作区没改完（Q09-24、Q09-25、Q09-26）
- 一次提交同时改了不相关的内容，怎样拆开来看或部分暂存（Q09-27）
- 密钥或密码一旦提交进历史，第一步永远是吊销/轮换，而不是先删除记录（Q09-28）
- 用 `blame` 或 `log -S` 找出谁在什么时候改了某一行、某段代码（Q09-29、Q09-30）

## 自测题库

### Q09-01 三个区域与 `add`

- 类型：代码题
- 出处：[Pro Git 2.2 记录每次更新到仓库](https://git-scm.com/book/zh/v2/Git-基础-记录每次更新到仓库)
- 问题：新建一个文件后，`git status` 分别在什么阶段显示什么？

```bash
git init -q
echo hi > a.txt
git status --short
git add a.txt
git status --short
```

- 答案：

```text
?? a.txt
A  a.txt
```

`??` 表示未跟踪的文件，只存在于工作区；`git add` 把它放进暂存区，`A` 表示"待提交的新增文件"。工作区是你正在编辑的文件，暂存区是下次提交将要包含的内容。

### Q09-02 `commit` 把暂存区存成一次快照

- 类型：代码题
- 出处：[Pro Git 2.2 记录每次更新到仓库](https://git-scm.com/book/zh/v2/Git-基础-记录每次更新到仓库)
- 问题：提交之后，`git status` 和 `git log` 分别显示什么？

```bash
git init -q
echo hi > a.txt
git add a.txt
git commit -q -m "add a.txt"
git status --short
git log --oneline | sed 's/^[0-9a-f]* /<hash> /'
```

- 答案：

```text
<hash> add a.txt
```

提交之后工作区、暂存区、仓库三者一致，`git status --short` 没有输出。`git log` 显示提交历史，这里把每次运行都不同的哈希替换成了 `<hash>`。

### Q09-03 `diff` 看的是哪两个区域

- 类型：易错点
- 出处：[Pro Git 2.2 记录每次更新到仓库](https://git-scm.com/book/zh/v2/Git-基础-记录每次更新到仓库)
- 问题：改动文件后不加 `--staged`、加 `--staged`，`git diff` 分别比较什么？

```bash
git init -q
echo one > a.txt
git add a.txt
git commit -q -m init
echo two >> a.txt
git diff | grep -c '^+two'
git diff --staged | grep -c '^+two'
git add a.txt
git diff | grep -c '^+two'
git diff --staged | grep -c '^+two'
```

- 答案：

```text
1
0
0
1
```

`git diff`（不加参数）比较工作区与暂存区；`git diff --staged` 比较暂存区与最近一次提交。`git add` 之后，改动进了暂存区，第一个命令就看不到它了，第二个能看到。

### Q09-04 `log` 的常用形式

- 类型：代码题
- 出处：[Pro Git 2.3 查看提交历史](https://git-scm.com/book/zh/v2/Git-基础-查看提交历史)
- 问题：`--oneline` 和 `-p` 分别显示什么？

```bash
git init -q
echo a > f.txt
git add f.txt
git commit -q -m first
echo b >> f.txt
git add f.txt
git commit -q -m second
git log --oneline | wc -l
git log -p -1 | grep -c '^+b'
```

- 答案：

```text
2
1
```

`--oneline` 把每次提交压缩成一行，方便看整体历史；`-p` 显示每次提交的具体差异（补丁），`-1` 只看最近一次。

### Q09-05 `.gitignore`

- 类型：代码题
- 出处：[Pro Git 2.2 记录每次更新到仓库：忽略文件](https://git-scm.com/book/zh/v2/Git-基础-记录每次更新到仓库)
- 问题：写了 `.gitignore` 之后，`*.log` 文件还会出现在 `git status` 里吗？

```bash
git init -q
echo '*.log' > .gitignore
touch debug.log keep.txt
git status --short
```

- 答案：

```text
?? .gitignore
?? keep.txt
```

`.gitignore` 里列出的匹配模式，会让 Git 在 `status`、`add .` 等操作中不再提示这些文件，但已经被跟踪的文件不受影响（需要先 `git rm --cached` 移出跟踪）。

### Q09-06 提交信息：标题与正文

- 类型：概念题
- 出处：[How to Write a Git Commit Message](https://chris.beams.io/posts/git-commit/)
- 问题：一条规范的提交信息应该长什么样？
- 答案：

按该文的七条规则：标题行与正文之间空一行分隔；标题行不超过 50 个字符；标题首字母大写；标题末尾不加句号；标题用祈使语气（比如"修复……"而不是"修复了……"或"修复中"）；正文每行不超过 72 个字符换行；正文用来解释改了什么、为什么这样改，而不是怎么改的（怎么改的，diff 本身已经说明了）。

### Q09-07 祈使语气

- 类型：概念题
- 出处：[How to Write a Git Commit Message](https://chris.beams.io/posts/git-commit/)
- 问题：`"Fixed bug"`、`"Fixes bug"`、`"Fix bug"` 哪个符合祈使语气？
- 答案：

`"Fix bug"`。判断方法是把标题填进这句话："如果应用这个提交，它将会 ___"，只有祈使语气能通顺地填进去："它将会 Fix bug"。这样写是因为 Git 自己生成的提交信息（如合并、还原）也是这种语气，保持一致。

### Q09-08 分支是一个指针

- 类型：代码题
- 出处：[Pro Git 3.1 分支简介](https://git-scm.com/book/zh/v2/Git-分支-分支简介)
- 问题：新建分支之后，`HEAD` 指向哪里？切换分支呢？

```bash
git init -q -b main
echo a > f.txt
git add f.txt
git commit -q -m init
git branch feature
cat .git/HEAD
git switch -q feature
cat .git/HEAD
```

- 答案：

```text
ref: refs/heads/main
ref: refs/heads/feature
```

分支只是一个指向某次提交的轻量指针，创建分支几乎不花时间。`HEAD` 是一个特殊指针，指向"当前所在的分支"，切换分支就是让 `HEAD` 指向别处。

### Q09-09 提交之后分支指针自动前移

- 类型：代码题
- 出处：[Pro Git 3.1 分支简介](https://git-scm.com/book/zh/v2/Git-分支-分支简介)
- 问题：在某个分支上提交之后，这个分支的指针会怎样？

```bash
git init -q -b main
echo a > f.txt; git add f.txt; git commit -q -m c1
c1=$(git rev-parse main)
echo b >> f.txt; git add f.txt; git commit -q -m c2
c2=$(git rev-parse main)
[ "$c1" != "$c2" ] && echo "分支指针变了"
echo "<hash>"
[ "$(git rev-parse HEAD)" = "$c2" ] && echo "HEAD 等于当前分支"
```

- 答案：

```text
分支指针变了
<hash>
HEAD 等于当前分支
```

每次提交，当前分支的指针都会自动移动到新提交上；`HEAD` 跟着当前分支一起移动。

### Q09-10 快进合并

- 类型：代码题
- 出处：[Pro Git 3.2 分支的新建与合并](https://git-scm.com/book/zh/v2/Git-分支-分支的新建与合并)
- 问题：如果 main 分支自创建 feature 后就没再提交过，合并 feature 会产生新的合并提交吗？

```bash
git init -q -b main
echo a > f.txt; git add f.txt; git commit -q -m c1
git switch -q -c feature
echo b >> f.txt; git add f.txt; git commit -q -m c2
git switch -q main
git merge --quiet feature
git log --oneline | wc -l
```

- 答案：

```text
2
```

main 自从分出 feature 后没有新提交，Git 只需要把 main 的指针直接移动到 feature 所指的提交，这叫快进（fast-forward），不产生新的合并提交，历史仍然只有 2 次提交。

### Q09-11 三方合并会产生一个新提交

- 类型：代码题
- 出处：[Pro Git 3.2 分支的新建与合并](https://git-scm.com/book/zh/v2/Git-分支-分支的新建与合并)
- 问题：如果两个分支各自都有新提交，合并会怎样？

```bash
git init -q -b main
echo a > f.txt; git add f.txt; git commit -q -m c1
git switch -q -c feature
echo b >> f.txt; git add f.txt; git commit -q -m c2
git switch -q main
echo c > g.txt; git add g.txt; git commit -q -m c3
git merge --quiet -m merge feature
git log --oneline | wc -l
git log --merges --oneline | wc -l
```

- 答案：

```text
4
1
```

两边都有新提交时无法快进，Git 会基于两边的共同祖先做一次三方合并，生成一个有两个父提交的新提交（合并提交），历史里能看到 4 次提交，其中 1 次是合并提交。

### Q09-12 合并冲突

- 类型：代码题
- 出处：[Pro Git 3.2 分支的新建与合并：遇到冲突时的分支合并](https://git-scm.com/book/zh/v2/Git-分支-分支的新建与合并)
- 问题：两个分支改了同一行，合并时会怎样？冲突标记长什么样？

```bash
git init -q -b main
echo line1 > f.txt; git add f.txt; git commit -q -m init
git switch -q -c feature
echo changed-by-feature > f.txt; git add f.txt; git commit -q -m c2
git switch -q main
echo changed-by-main > f.txt; git add f.txt; git commit -q -m c3
git merge feature 2>&1 | grep -o "CONFLICT"
grep -c '^<<<<<<<\|^=======\|^>>>>>>>' f.txt
```

- 答案：

```text
CONFLICT
3
```

两个分支对同一行做了不同的修改，Git 无法自动决定用哪一个，合并会停下来并报告冲突，在文件里插入 `<<<<<<<`、`=======`、`>>>>>>>` 标记出两边的内容，需要手动编辑、`git add` 标记为已解决，再完成提交。

### Q09-13 变基与合并达到相似的最终内容

- 类型：代码题
- 出处：[Pro Git 3.6 变基](https://git-scm.com/book/zh/v2/Git-分支-变基)
- 问题：变基之后，`feature` 分支的提交历史会怎样变化？

```bash
git init -q -b main
echo a > f.txt; git add f.txt; git commit -q -m c1
git switch -q -c feature
echo b >> f.txt; git add f.txt; git commit -q -m c2
git switch -q main
echo c > g.txt; git add g.txt; git commit -q -m c3
git switch -q feature
git rebase --quiet main
git log --oneline main..feature | wc -l
git merge-base --is-ancestor main feature && echo "main 是 feature 的祖先"
```

- 答案：

```text
1
main 是 feature 的祖先
```

变基把 `feature` 上的提交（`c2`）在 `main` 的最新提交（`c3`）之后重新生成一遍，得到内容相同但哈希不同的新提交。变基之后，`main` 变成了 `feature` 历史的直接祖先，历史看起来像一条直线，而不是合并产生的分叉。

### Q09-14 变基的适用边界

- 类型：概念题
- 出处：[Pro Git 3.6 变基：变基的风险](https://git-scm.com/book/zh/v2/Git-分支-变基)
- 问题：什么情况下不应该使用变基？
- 答案：

Pro Git 把这条规则称为"金科玉律"：如果提交已经存在于你的仓库之外（已经推送，别人可能已经拉取并在此基础上开发），就不要对它变基。变基的本质是丢弃原来的提交、创建内容相似但实际不同的新提交；如果别人已经基于旧提交继续开发，你变基之后历史对不上，会给协作带来混乱。只对还没有分享出去的本地提交变基是安全的。

### Q09-15 `restore` 撤销工作区的修改

- 类型：代码题
- 出处：[Pro Git 2.4 撤消操作](https://git-scm.com/book/zh/v2/Git-基础-撤消操作)
- 问题：改错了一个文件、还没有 `add`，怎样撤销？

```bash
git init -q
echo original > f.txt
git add f.txt; git commit -q -m init
echo oops >> f.txt
git restore f.txt
cat f.txt
```

- 答案：

```text
original
```

`git restore 文件` 把工作区里的文件恢复成最近一次提交（或暂存区，如果加了 `--staged`）时的样子，未提交的修改会永久丢失，操作前要确认。

### Q09-16 `reset` 回退提交

- 类型：代码题
- 出处：[Pro Git 2.4 撤消操作](https://git-scm.com/book/zh/v2/Git-基础-撤消操作)、[7.7 重置揭密](https://git-scm.com/book/zh/v2/Git-工具-重置揭密)
- 问题：`git reset --hard HEAD~1` 之后，最近一次提交去哪了？工作区呢？

```bash
git init -q
echo a > f.txt; git add f.txt; git commit -q -m c1
echo b >> f.txt; git add f.txt; git commit -q -m c2
git reset --hard -q HEAD~1
git log --oneline | wc -l
cat f.txt
```

- 答案：

```text
1
a
```

`reset --hard` 把当前分支指针移回上一个提交，并让工作区和暂存区都变成那个提交时的样子，`c2` 引入的改动从工作区消失。`--hard` 会丢弃未提交的改动，使用前要确认；对已经分享出去的提交做 `reset` 也和变基一样，会造成历史不一致。

### Q09-17 `revert` 用新提交抵消旧提交

- 类型：代码题
- 出处：[Pro Git 2.4 撤消操作](https://git-scm.com/book/zh/v2/Git-基础-撤消操作)
- 问题：`revert` 和 `reset --hard` 都能让文件内容回到之前，区别是什么？

```bash
git init -q
echo a > f.txt; git add f.txt; git commit -q -m c1
echo b >> f.txt; git add f.txt; git commit -q -m c2
git revert --quiet --no-edit HEAD >/dev/null
cat f.txt
git log --oneline | wc -l
```

- 答案：

```text
a
3
```

`revert` 不删除历史，而是新增一个提交，把之前提交的改动反过来做一遍，所以历史里能看到 3 次提交，`c2` 仍然存在，只是被第 3 次提交抵消了效果。已经推送、别人可能已拉取的提交，用 `revert` 比用 `reset` 或变基更安全。

### Q09-18 `reflog` 找回提交

- 类型：代码题
- 出处：[Pro Git 7.7 重置揭密](https://git-scm.com/book/zh/v2/Git-工具-重置揭密)
- 问题：`reset --hard` 之后，被丢弃的提交真的立刻消失了吗？

```bash
git init -q
echo a > f.txt; git add f.txt; git commit -q -m c1
echo b >> f.txt; git add f.txt; git commit -q -m c2
lost=$(git rev-parse HEAD)
git reset --hard -q HEAD~1
git cat-file -t "$lost"
git reflog | grep -c "$( echo "$lost" | cut -c1-7 )"
```

- 答案：

```text
commit
1
```

Git 的提交对象在被真正的垃圾回收清理之前一直存在于仓库里，`reset` 只是移动了分支指针，没有立刻删除对象。`git reflog` 记录了 `HEAD` 最近的移动过程，可以从中找到"丢失"的提交哈希，用 `git reset --hard 哈希` 或 `git branch 新分支名 哈希` 找回来。

### Q09-19 提交对象里有什么

- 类型：概念题
- 出处：[Pro Git 10.2 Git 对象](https://git-scm.com/book/zh/v2/Git-内部原理-Git-对象)
- 问题：一次提交记录了哪些信息？
- 答案：

一个提交对象包含：这次提交时项目文件的快照（通过树对象引用）、作者与提交者的姓名邮箱和时间、提交信息，以及指向上一个提交的指针（父提交，第一次提交没有父提交，合并提交有两个父提交）。正是"指向上一个提交"这一条，让所有提交连成一条历史链。

### Q09-20 同样的内容，`add` 两次得到同一个对象

- 类型：代码题
- 出处：[Pro Git 10.2 Git 对象](https://git-scm.com/book/zh/v2/Git-内部原理-Git-对象)
- 问题：两个内容相同的文件，Git 会存两份数据吗？

```bash
git init -q
echo same-content > a.txt
cp a.txt b.txt
git add a.txt b.txt
git commit -q -m init
git ls-tree HEAD | awk '{print $3}' | sort -u | wc -l
```

- 答案：

```text
1
```

Git 按内容计算哈希来存储对象（blob），内容完全相同的文件对应同一个 blob 对象，即使文件名不同，仓库里也只存一份数据，这也是 Git 存储高效的原因之一。

### Q09-21 `clone` 与 `remote -v`

- 类型：代码题
- 出处：[Pro Git 2.5 远程仓库的使用](https://git-scm.com/book/zh/v2/Git-基础-远程仓库的使用)
- 问题：`clone` 之后自动配置了什么？

```bash
git init -q --bare origin.git
git clone -q origin.git work >/dev/null 2>&1
cd work
git remote -v | awk '{print $1, $3}' | sort -u
```

- 答案：

```text
origin (fetch)
origin (push)
```

`git clone` 会把远程仓库完整下载下来，并自动把它命名为 `origin`，同时记录抓取和推送两个地址（这里相同）。之后 `git fetch`、`git push` 不加参数时默认操作的就是 `origin`。

### Q09-22 `fetch` 不会自动合并，`pull` 会

- 类型：易错点
- 出处：[Pro Git 2.5 远程仓库的使用](https://git-scm.com/book/zh/v2/Git-基础-远程仓库的使用)
- 问题：`fetch` 之后本地分支变了吗？

```bash
git init -q --bare origin.git
git clone -q origin.git a >/dev/null 2>&1
git clone -q origin.git b >/dev/null 2>&1
(cd a && echo x > f.txt && git add f.txt && git commit -q -m c1 && git push -q origin HEAD:main)
cd b
git fetch -q origin
git log --oneline main 2>/dev/null | wc -l
git log --oneline origin/main | wc -l
```

- 答案：

```text
0
1
```

`fetch` 只是把远程的新提交下载到本地的 `origin/main` 这个远程跟踪分支，不改动本地的 `main`；`main` 因为还没有任何提交所以 `git log main` 报错、行数为 0。`git pull` 相当于 `fetch` 之后再自动 `merge`（或 `rebase`），才会把远程的改动合并进当前分支。

### Q09-23 `push` 需要先有共同的历史

- 类型：概念题
- 出处：[Pro Git 2.5 远程仓库的使用](https://git-scm.com/book/zh/v2/Git-基础-远程仓库的使用)
- 问题：别人已经推送过新提交，你没有先拉取就直接 `push`，会怎样？
- 答案：

Git 会拒绝这次推送，提示远程有你本地没有的提交（不是快进关系）。这是一种保护机制，避免直接覆盖别人的工作。正确做法是先 `git fetch` 或 `git pull` 把远程的新提交合并或变基到本地，解决可能的冲突，再推送。

### Q09-24 改最后一条提交信息

- 类型：代码题
- 出处：[Pro Git 2.4 撤消操作](https://git-scm.com/book/zh/v2/Git-基础-撤消操作)
- 问题：提交信息打错字了，还没推送，怎么改？

```bash
git init -q
echo a > f.txt; git add f.txt; git commit -q -m "fix bgu"
git commit -q --amend -m "fix bug"
git log --oneline | sed 's/^[0-9a-f]* //'
```

- 答案：

```text
fix bug
```

`commit --amend` 用一次新提交替换最近一次提交（信息或内容都可以改），历史上看起来像是原来的提交被"修正"了，但底层其实是产生了一个新的提交对象。因为哈希变了，已经推送过的提交不要用这种方式改。

### Q09-25 提交时漏了一个文件

- 类型：代码题
- 出处：[Pro Git 2.4 撤消操作](https://git-scm.com/book/zh/v2/Git-基础-撤消操作)
- 问题：提交完才发现漏加了一个文件，怎样补进刚才那次提交，而不是新建一次？

```bash
git init -q
echo a > f.txt; git add f.txt; git commit -q -m "init"
echo b > g.txt
git add g.txt
git commit -q --amend --no-edit
git show --stat HEAD | grep -c 'g.txt'
git log --oneline | wc -l
```

- 答案：

```text
1
1
```

`--amend` 把当前暂存区的内容并入最近一次提交，`--no-edit` 表示不修改提交信息。结果只有 1 次提交，但它现在同时包含 `f.txt` 和 `g.txt`。

### Q09-26 工作区没改完，需要临时切走

- 类型：代码题
- 出处：[Pro Git 7.3 贮藏与清理](https://git-scm.com/book/zh/v2/Git-工具-贮藏与清理)
- 问题：改到一半，需要切到别的分支处理紧急问题，又不想提交半成品，怎么办？

```bash
git init -q -b main
echo a > f.txt; git add f.txt; git commit -q -m init
echo wip >> f.txt
git stash push -q -m "half done"
git status --short
git stash pop -q
cat f.txt
```

- 答案：

```text
a
wip
```

`stash` 把工作区和暂存区里未提交的改动收起来，恢复成最近一次提交的干净状态（这时 `status --short` 没有输出），可以放心切换分支处理别的事；`stash pop` 把收起来的改动重新应用回来并从贮藏列表移除。

### Q09-27 只暂存文件里的一部分改动

- 类型：概念题
- 出处：[Pro Git 7.2 交互式暂存](https://git-scm.com/book/zh/v2/Git-工具-交互式暂存)
- 问题：一个文件里改了两处，只想提交其中一处，怎么办？
- 答案：

用 `git add --patch`（简写 `-p`）或 `git add --interactive`。Git 会把改动拆成一个个"块"，让你逐块选择是否加入暂存区，从而做出比"整份文件提交"更精细的提交，让每次提交只做一件事，历史更清楚、也更方便日后用 `revert` 或 `bisect` 定位问题。

### Q09-28 密钥泄露进了历史记录

- 类型：概念题
- 出处：[GitHub 文档：从仓库中移除敏感数据](https://docs.github.com/zh/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)
- 问题：不小心把一个密钥提交并推送到了远程仓库，第一步该做什么？
- 答案：

GitHub 官方文档明确写着：如果要移除的敏感数据是一个密钥（密码、令牌、凭证等），第一步永远是**吊销或轮换**这个密钥。一旦它被吊销或轮换，就不能再用来访问任何东西了，这本身可能已经解决了问题。之后再考虑要不要用改写历史等方式把它从仓库记录里清除——改写历史步骤复杂、副作用多，而且即使清除了，已经被别人克隆或缓存过的旧历史仍可能包含它，所以让密钥本身失效才是真正靠得住的办法。密钥一旦提交，就该当作已经泄露处理。

### Q09-29 `blame` 找出谁改了哪一行

- 类型：代码题
- 出处：[Pro Git 7.5 搜索](https://git-scm.com/book/zh/v2/Git-工具-搜索)
- 问题：怎样知道文件里某一行是哪次提交引入的？

```bash
git init -q
printf 'line1\n' > f.txt; git add f.txt; git commit -q -m c1
printf 'line1\nline2\n' > f.txt; git add f.txt; git commit -q -m c2
git blame f.txt --porcelain | grep -c '^summary c2'
```

- 答案：

```text
1
```

`git blame 文件` 逐行标出每一行最后一次是被哪个提交、哪个作者修改的。这里 `line2` 应该被标记为来自提交 `c2`。

### Q09-30 `log -S` 找出何时引入了某段代码

- 类型：代码题
- 出处：[Pro Git 7.5 搜索](https://git-scm.com/book/zh/v2/Git-工具-搜索)
- 问题：想知道某个函数名是在哪次提交里第一次出现的，`blame` 够用吗？还有什么办法？

```bash
git init -q
echo 'def old():pass' > f.py; git add f.py; git commit -q -m c1
echo 'def new_func():pass' >> f.py; git add f.py; git commit -q -m c2
git log --oneline -S 'new_func' | sed 's/^[0-9a-f]* //'
```

- 答案：

```text
c2
```

`blame` 只能告诉你当前这一行最后是谁改的，如果一段代码被删除又重新加回，或者要找的是"什么时候第一次出现某个字符串"而不针对某一行，用 `git log -S 字符串` 更合适：它会找出所有让该字符串的出现次数发生变化的提交。
