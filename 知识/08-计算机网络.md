## 概念清单

学完主题 8 后，下面每一条都应能用一两句话解释并举出例子。括号里是对应的题目。

### 基本模型

- IP 地址标识网络上的一台主机，端口号标识这台主机上的一个具体服务（Q08-01、Q08-02）
- 一个端口同一时刻只能被一个进程独占监听（Q08-03）
- 客户端-服务器模型：服务器监听，客户端主动连接（Q08-04）

### TCP 与 UDP

- TCP 面向连接，保证数据按顺序、不丢失地到达；建立连接需要先握手（Q08-05、Q08-06）
- UDP 不需要建立连接，不保证送达，但更轻量、延迟更低（Q08-07）
- 两个使用相同 IP 和端口的连接，可以用四元组（源 IP、源端口、目的 IP、目的端口）区分（Q08-08）

### 字节序与网络传输

- 网络字节序是大端；不同机器之间传输多字节数据需要转换字节序（Q08-09，与主题 6 的 Q06-06 相衔接）

### HTTP

- HTTP 是建立在 TCP 之上的应用层协议，请求和响应都是纯文本格式（Q08-10）
- HTTP 请求由请求行、请求头、空行、请求体组成；响应类似（Q08-11、Q08-12）
- 状态码的含义：2xx 成功、3xx 重定向、4xx 客户端错误、5xx 服务器错误（Q08-13）
- `Content-Type` 告诉客户端怎样解释响应体的数据（Q08-14）

### 协议分层

- 应用层（HTTP）建立在传输层（TCP/UDP）之上，传输层建立在网络层（IP）之上，各层只关心自己这一层的问题（Q08-15）
- DNS 把域名解析成 IP 地址，是访问网站的第一步（Q08-16）

## 自测题库

### Q08-01 IP 地址与端口

- 类型：代码题
- 出处：[Python 官方文档：socket 模块](https://docs.python.org/zh-cn/3/library/socket.html)
- 问题：一个 socket 绑定到"随便一个空闲端口"，怎样知道操作系统实际分配了哪个端口？

```python
import socket

s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
s.bind(("127.0.0.1", 0))  # 端口填 0 表示让操作系统自动分配
host, port = s.getsockname()
print(host, port > 0, port <= 65535)
s.close()
```

- 答案：

```text
127.0.0.1 True True
```

`127.0.0.1` 是"回环地址"，专门指向本机自己，不经过真实的网卡。端口号是一个 16 位无符号整数，取值范围 0 到 65535，绑定时填 0 表示"由操作系统在当前未被占用的端口里自动挑一个"，`getsockname()` 能查到实际分配的是哪个。

### Q08-02 端口标识主机上的具体服务

- 类型：概念题
- 出处：TCP/IP 协议族的基本模型
- 问题：同一台机器上，为什么访问网页用 80 或 443 端口、收发邮件用别的端口，不会互相干扰？
- 答案：

一台机器只有一个（或几个）IP 地址，但同时可能运行着很多网络服务（网页服务器、邮件服务器、SSH 服务等）。IP 地址负责把数据包送到正确的主机，端口号则负责在这台主机内部，把数据交给正确的进程——相当于"IP 地址是小区地址，端口号是门牌号"。约定俗成的端口有 HTTP 用 80、HTTPS 用 443、SSH 用 22，但这些只是习惯，任何服务理论上都可以绑定到任意没被占用的端口。

### Q08-03 端口被独占

- 类型：代码题
- 出处：[Python 官方文档：socket.bind](https://docs.python.org/zh-cn/3/library/socket.html#socket.socket.bind)
- 问题：两个进程能同时监听同一个端口吗？

```python
import socket

s1 = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
s1.bind(("127.0.0.1", 0))
port = s1.getsockname()[1]
s1.listen(1)

s2 = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
try:
    s2.bind(("127.0.0.1", port))
    print("绑定成功")
except OSError as e:
    print("绑定失败:", type(e).__name__)
s1.close()
```

- 答案：

```text
绑定失败: OSError
```

一个端口在同一时刻只能被一个监听中的 socket 独占（不考虑一些高级的端口复用选项）。第二个 socket 尝试绑定到已经被占用的端口会失败，抛出 `OSError`（常见的提示是"地址已被使用"）。这也是为什么开发时如果程序没有正常关闭旧的监听 socket，重新启动可能会报"端口被占用"。

### Q08-04 客户端-服务器模型

- 类型：代码题
- 出处：[Python 官方文档：socket.accept](https://docs.python.org/zh-cn/3/library/socket.html#socket.socket.accept)
- 问题：TCP 通信里，谁先监听、谁先连接？

```python
import socket
import threading

def server(sock, result):
    conn, addr = sock.accept()
    result.append(addr[0])
    conn.close()

srv = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
srv.bind(("127.0.0.1", 0))
port = srv.getsockname()[1]
srv.listen(1)

result = []
t = threading.Thread(target=server, args=(srv, result))
t.start()

client = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
client.connect(("127.0.0.1", port))
client.close()
t.join()
print(result)
srv.close()
```

- 答案：

```text
['127.0.0.1']
```

服务器先 `bind` 占用一个端口、`listen` 开始监听，等待有人连进来；客户端主动 `connect` 到服务器的地址和端口，发起连接。`accept()` 会阻塞（暂停程序）直到有客户端连进来，然后返回一个新的 socket（专门服务这个客户端）和对方的地址。这是几乎所有网络服务共同的基本模式。

### Q08-05 TCP 保证数据按顺序到达

- 类型：代码题
- 出处：[Python 官方文档：socket 模块](https://docs.python.org/zh-cn/3/library/socket.html)（TCP 是 SOCK_STREAM，提供可靠的字节流）
- 问题：连续发送多次数据，接收方读到的顺序会乱吗？

```python
import socket
import threading

def server(sock):
    conn, _ = sock.accept()
    data = b""
    while len(data) < 15:
        data += conn.recv(1024)
    conn.close()
    return data

srv = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
srv.bind(("127.0.0.1", 0))
port = srv.getsockname()[1]
srv.listen(1)

result = []
def run():
    result.append(server(srv))
t = threading.Thread(target=run)
t.start()

client = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
client.connect(("127.0.0.1", port))
client.sendall(b"AAAAA")
client.sendall(b"BBBBB")
client.sendall(b"CCCCC")
client.close()
t.join()
print(result[0])
srv.close()
```

- 答案：

```text
b'AAAAABBBBBCCCCC'
```

TCP（`SOCK_STREAM`）把连接两端的数据看作一条连续的字节流，保证发送方写入的字节，接收方一定按同样的顺序收到，不会乱序、不会丢失（网络异常时会自动重传）。这里连续三次 `sendall`，接收方读到的字节完全按发送顺序拼接起来，即使底层网络可能把它们拆成不同的包传输、或者接收方分几次 `recv` 才读完，也感知不到这些细节——TCP 把这些复杂性隐藏起来，暴露给程序的是一个简单的"可靠字节流"接口。

### Q08-06 建立 TCP 连接才能收发数据

- 类型：代码题
- 出处：[Python 官方文档：socket.connect](https://docs.python.org/zh-cn/3/library/socket.html#socket.socket.connect)
- 问题：没有先连接，直接往一个 TCP socket 里发数据会怎样？

```python
import socket

s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
try:
    s.send(b"hi")
except OSError as e:
    print(isinstance(e, OSError), type(e).__name__)
s.close()
```

- 答案：

```text
True BrokenPipeError
```

TCP 是"面向连接"的协议：必须先完成连接的建立（客户端 `connect`、服务器 `accept`），才能在这条连接上收发数据。没有先建立连接就尝试发送，会失败并抛出异常：具体的异常类是 `BrokenPipeError`（它是 `OSError` 的子类），提示对端连接不存在。这和 UDP（Q08-07）不需要先建立连接、可以直接把数据报发给任意目标地址形成对比。

### Q08-07 UDP 不需要建立连接

- 类型：代码题
- 出处：[Python 官方文档：socket 模块](https://docs.python.org/zh-cn/3/library/socket.html)（UDP 是 SOCK_DGRAM）
- 问题：UDP 发数据前需要先"连接"对方吗？

```python
import socket

receiver = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
receiver.bind(("127.0.0.1", 0))
port = receiver.getsockname()[1]

sender = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
sender.sendto(b"ping", ("127.0.0.1", port))  # 没有 connect，直接发

data, addr = receiver.recvfrom(1024)
print(data)
receiver.close()
sender.close()
```

- 答案：

```text
b'ping'
```

UDP（`SOCK_DGRAM`，数据报套接字）不需要先建立连接，`sendto` 直接把一个独立的数据包（数据报）发给指定的地址，对方收到与否、顺序对不对，协议本身不保证。这让 UDP 比 TCP 轻量、延迟更低，适合视频通话、DNS 查询这类"偶尔丢一点数据也能接受，但延迟必须低"的场景；需要可靠传输的场景（如文件传输、网页请求）则用 TCP。

### Q08-08 四元组区分连接

- 类型：概念题
- 出处：TCP 连接的标识方式
- 问题：一台服务器的 80 端口能同时服务成千上万个客户端，是怎么区分这些连接的？
- 答案：

一条 TCP 连接由四个信息共同确定：源 IP、源端口、目的 IP、目的端口，合称"四元组"。服务器的 IP 和端口（目的 IP、目的端口）对所有连接来说是相同的，但每个连接过来的客户端 IP 和端口（源 IP、源端口）各不相同，四元组的组合因此能唯一区分出成千上万条同时存在的连接，操作系统靠这个四元组把收到的数据包分发给正确的那条连接，不会混在一起。

### Q08-09 网络字节序

- 类型：代码题
- 出处：[Python 官方文档：socket.htons](https://docs.python.org/zh-cn/3/library/socket.html#socket.htons)；与主题 6 的 Q06-06 相衔接
- 问题：`htons` 是做什么的？为什么网络传输需要它？

```python
import socket
import sys

value = 1
network_order = socket.htons(value)
print(sys.byteorder, network_order)
```

- 答案：

```text
little 256
```

网络协议约定统一使用大端字节序（"网络字节序"），但很多机器（包括常见的 x86-64）内部用小端存储数字（主题 6 的 Q06-06）。`htons`（host to network short）把一个 16 位整数从主机字节序转换成网络字节序，`ntohs` 做反向转换。这里主机是小端，`1` 在小端表示是字节 `01 00`，转换成大端字节序后被当作数值 `0x0100`（即 256）解读，防止两台字节序不同的机器直接把对方发来的原始字节按自己的字节序误读成不同的数字。

### Q08-10 HTTP 建立在 TCP 之上

- 类型：代码题
- 出处：[Python 官方文档：http.server](https://docs.python.org/zh-cn/3/library/http.server.html)
- 问题：一个简单的 HTTP 服务器，本质上是在 TCP 连接上做什么？

```python
import http.server
import threading
import urllib.request

class Handler(http.server.BaseHTTPRequestHandler):
    def do_GET(self):
        self.send_response(200)
        self.send_header("Content-Type", "text/plain")
        self.end_headers()
        self.wfile.write(b"hello")

    def log_message(self, *args):
        pass

srv = http.server.HTTPServer(("127.0.0.1", 0), Handler)
port = srv.server_port
t = threading.Thread(target=srv.serve_forever, daemon=True)
t.start()

resp = urllib.request.urlopen(f"http://127.0.0.1:{port}/")
print(resp.status, resp.read())
srv.shutdown()
```

- 答案：

```text
200 b'hello'
```

HTTP 服务器的底层仍然是 Q08-04 那套"监听、接受连接"的 TCP 模式，只是在建立好的 TCP 连接上，按照 HTTP 协议约定的文本格式来解析请求、构造响应——HTTP 不是另一种传输方式，而是一套"双方在 TCP 字节流上怎样组织文本内容"的约定。`http.server` 模块帮你处理了 TCP 层面的细节，只需要实现 `do_GET` 这样的方法来决定收到请求后怎么响应。

### Q08-11 HTTP 请求报文的格式

- 类型：代码题
- 出处：HTTP/1.1 请求报文的标准格式（请求行、请求头、空行、请求体）
- 问题：一个 GET 请求的原始报文长什么样？

```python
import http.server
import threading
import socket

class Handler(http.server.BaseHTTPRequestHandler):
    def do_GET(self):
        self.send_response(200)
        self.end_headers()
        self.wfile.write(b"ok")

    def log_message(self, *args):
        pass

srv = http.server.HTTPServer(("127.0.0.1", 0), Handler)
port = srv.server_port
t = threading.Thread(target=srv.serve_forever, daemon=True)
t.start()

s = socket.create_connection(("127.0.0.1", port))
s.sendall(b"GET / HTTP/1.1\r\nHost: localhost\r\nConnection: close\r\n\r\n")
data = b""
while True:
    chunk = s.recv(4096)
    if not chunk:
        break
    data += chunk
print(data.split(b"\r\n")[0])
srv.shutdown()
```

- 答案：

```text
b'HTTP/1.0 200 OK'
```

这里手动拼出了一个符合格式的 HTTP 请求发给服务器：第一行是请求行（方法、路径、协议版本），接下来是若干请求头（这里是 `Host` 和 `Connection`），一个空行表示请求头结束，GET 请求通常没有请求体。响应的第一行同样是状态行，格式是"协议版本 状态码 状态描述"——这里 Python 内置的简单服务器默认按 HTTP/1.0 协议回应。空行（`\r\n\r\n`）分隔头部和正文，这是 HTTP 报文能被正确解析的关键约定。

### Q08-12 HTTP 头部与正文之间的空行

- 类型：代码题
- 出处：HTTP 报文格式：头部结束后必须有一个空行
- 问题：接收方怎么知道头部读完了、正文从哪里开始？

```python
import http.server
import threading
import socket

class Handler(http.server.BaseHTTPRequestHandler):
    def do_GET(self):
        self.send_response(200)
        self.end_headers()
        self.wfile.write(b"body-content")

    def log_message(self, *args):
        pass

srv = http.server.HTTPServer(("127.0.0.1", 0), Handler)
port = srv.server_port
t = threading.Thread(target=srv.serve_forever, daemon=True)
t.start()

s = socket.create_connection(("127.0.0.1", port))
s.sendall(b"GET / HTTP/1.1\r\nHost: localhost\r\nConnection: close\r\n\r\n")
data = b""
while True:
    chunk = s.recv(4096)
    if not chunk:
        break
    data += chunk
head, body = data.split(b"\r\n\r\n", 1)
print(body)
srv.shutdown()
```

- 答案：

```text
b'body-content'
```

HTTP 报文用一个连续的空行（`\r\n\r\n`，两个连续的"回车换行"）来标记头部的结束，空行之后的内容就是正文。这里用 `split(b"\r\n\r\n", 1)` 精确地把响应拆成头部和正文两部分，正文正好是服务器写入的 `body-content`。这个约定看似简单，但正是 HTTP 报文能在纯文本流里被准确解析出结构的关键。

### Q08-13 状态码分类

- 类型：代码题
- 出处：HTTP 状态码的分类约定
- 问题：404 属于哪一类状态码？代表什么？

```python
import http.server
import threading
import urllib.request
import urllib.error

class Handler(http.server.BaseHTTPRequestHandler):
    def do_GET(self):
        self.send_response(404)
        self.end_headers()

    def log_message(self, *args):
        pass

srv = http.server.HTTPServer(("127.0.0.1", 0), Handler)
port = srv.server_port
t = threading.Thread(target=srv.serve_forever, daemon=True)
t.start()

try:
    urllib.request.urlopen(f"http://127.0.0.1:{port}/missing")
except urllib.error.HTTPError as e:
    print(e.code, 400 <= e.code < 500)
srv.shutdown()
```

- 答案：

```text
404 True
```

HTTP 状态码按第一位数字分类：2xx 表示成功（如 200 OK）；3xx 表示需要进一步操作，常见于重定向；4xx 表示客户端这边出了问题（比如 404 表示"请求的资源不存在"，401/403 和权限有关）；5xx 表示服务器那边出了问题（比如 500 表示服务器内部错误）。这套分类让客户端不需要理解每一个具体状态码，也能大致判断"是我这边的问题还是服务器那边的问题"。

### Q08-14 `Content-Type` 告诉客户端怎么解释数据

- 类型：代码题
- 出处：HTTP 头部字段 `Content-Type` 的作用
- 问题：同样是一段字节，怎么区分它是纯文本还是 JSON？

```python
import http.server
import threading
import urllib.request

class Handler(http.server.BaseHTTPRequestHandler):
    def do_GET(self):
        self.send_response(200)
        self.send_header("Content-Type", "application/json")
        self.end_headers()
        self.wfile.write(b'{"ok": true}')

    def log_message(self, *args):
        pass

srv = http.server.HTTPServer(("127.0.0.1", 0), Handler)
port = srv.server_port
t = threading.Thread(target=srv.serve_forever, daemon=True)
t.start()

resp = urllib.request.urlopen(f"http://127.0.0.1:{port}/")
print(resp.getheader("Content-Type"))
srv.shutdown()
```

- 答案：

```text
application/json
```

HTTP 报文本身只是一串字节，`Content-Type` 这个响应头告诉客户端应该按什么格式去解释正文的这些字节：`text/plain` 是纯文本，`text/html` 是网页，`application/json` 是 JSON 数据，`image/png` 是图片。浏览器和各种 HTTP 客户端库都依赖这个字段来决定"怎么显示或解析收到的内容"，写错了 `Content-Type` 是常见的接口联调问题之一。

### Q08-15 协议分层

- 类型：概念题
- 出处：TCP/IP 协议族的分层模型
- 问题：HTTP、TCP、IP 分别负责什么？为什么要分层？
- 答案：

自上而下：应用层（如 HTTP）负责定义"传的是什么内容、什么格式"，不关心数据怎么被送达；传输层（TCP/UDP）负责"数据要不要保证送达、按不按顺序"，不关心内容是什么、走哪条物理路径；网络层（IP）负责"怎样把一个数据包从一台主机送到另一台主机"，不关心里面装的是什么。每一层只依赖下一层提供的服务，不需要知道下一层具体怎么实现——这正是主题 6 里"抽象层次"（Q06 的相关内容与主题 1 的 Q01-29）思想在网络领域的体现：HTTP 完全不需要关心底层是以太网还是 WiFi，TCP 也不需要关心上层跑的是 HTTP 还是别的协议，改动某一层不会波及其他层。

### Q08-16 DNS：域名解析成 IP 地址

- 类型：概念题
- 出处：DNS（域名系统）的基本作用
- 问题：为什么访问网站可以用好记的域名（如 `example.com`），而不需要记住一长串 IP 地址？
- 答案：

网络上真正用来定位主机、建立连接的是 IP 地址（Q08-01），但 IP 地址不好记、也可能变化。DNS（域名系统）提供了一套"域名到 IP 地址"的查询服务：在浏览器地址栏输入一个域名后，客户端会先向 DNS 服务器查询这个域名对应的 IP 地址，拿到 IP 之后才真正发起 TCP 连接。这个过程通常在几十毫秒内自动完成，用户感觉不到，但它是访问一个网站时，在建立 TCP 连接（Q08-04）之前必须先完成的一步。本页的练习都在回环地址上进行，没有涉及真实的 DNS 查询，因为对外部域名的解析结果依赖当时的网络环境，不适合作为要求确定答案的自动化验证。
