## 概念清单

学完主题 7 后，下面每一条都应能用一两句话解释并举出例子。括号里是对应的题目。

### 进程

- `fork()` 创建一个几乎一样的子进程，父子进程各自独立拥有一份内存，之后互不影响（Q07-01、Q07-04、Q07-05）
- `fork()` 在父进程和子进程里的返回值不同：子进程里是 0，父进程里是子进程的 pid（Q07-01）
- `wait`/`waitpid` 让父进程等待子进程结束并取得它的退出状态（Q07-02、Q07-11）
- `exec` 系列调用会用新程序替换当前进程的内存空间，而不是创建新进程（Q07-06）
- 子进程会继承父进程的环境变量（与主题 0 的 Q00-25 相衔接）（Q07-07）

### 进程间通信

- 管道（pipe）：一端写、一端读，是父子进程之间传数据的简单方式（Q07-03）
- 共享内存（mmap）：多个进程直接读写同一块物理内存，不需要每次都拷贝数据（Q07-08）

### 信号

- 信号是操作系统通知进程"发生了某件事"的机制，进程可以注册处理函数来响应（Q07-09）
- 常见信号的默认行为：`SIGTERM` 终止进程；进程可以捕获、忽略，或使用默认行为（Q07-10、与主题 0 的 Q00-32 和主题 3 的 Q03-19 相衔接）

### 线程

- 同一进程内的多个线程共享同一份内存，这是线程和进程最根本的区别（Q07-12）
- 多个线程同时读写同一个变量而不加保护，会产生竞态条件，结果不可预测（Q07-13）
- 锁（Lock）用来保证同一时刻只有一个线程能进入某段代码，避免竞态（Q07-14）
- CPython 的全局解释器锁（GIL）确保同一时刻只有一个线程执行 Python 字节码，这限制了多线程在多核上的并行计算能力（Q07-15）
- 用多进程而不是多线程来利用多核 CPU 做计算密集型任务，是因为多进程不受 GIL 限制（Q07-16）
- I/O 操作会释放 GIL，所以多线程对"等待网络、等待磁盘"这类任务仍然有效（Q07-17）

### 死锁

- 死锁：多个执行者互相等待对方释放资源，谁都无法继续（Q07-18）

### 文件描述符与虚拟内存

- 文件描述符是一个小整数，0、1、2 默认分别是标准输入、标准输出、标准错误（Q07-19）
- 虚拟内存：每个进程看到的地址空间是独立的、"虚拟"的，由操作系统负责映射到真实的物理内存（Q07-20）

## 自测题库

### Q07-01 `fork` 的两个返回值

- 类型：代码题
- 出处：[Python 官方文档：os.fork](https://docs.python.org/zh-cn/3/library/os.html#os.fork)
- 问题：`fork()` 之后，父进程和子进程各自看到的返回值是什么？

```python
import os
import sys

pid = os.fork()
if pid == 0:
    print("child: fork 返回", pid)
    sys.stdout.flush()
    os._exit(0)
else:
    os.waitpid(pid, 0)
    print("parent: fork 返回子进程 pid", pid > 0)
```

- 答案：

```text
child: fork 返回 0
parent: fork 返回子进程 pid True
```

`fork()` 只调用一次，却"返回两次"：在新建的子进程里返回 0，在原来的父进程里返回子进程的真实 pid（一个正整数）。这是判断"我现在是父进程还是子进程"的标准方式：`if pid == 0` 表示这里是子进程分支。这道题里子进程用 `print` 之后紧跟 `os._exit`，特意加了 `sys.stdout.flush()`——原因和主题 3 的 Q03-19 一样：标准输出连到管道时是缓冲的，`os._exit` 不会像正常的 `sys.exit()` 或 `return` 那样触发退出清理（包括刷新缓冲区），子进程里写的内容如果不手动 `flush`，很可能连着子进程一起消失，父进程也看不到。

### Q07-02 `wait` 回收子进程

- 类型：代码题
- 出处：[Python 官方文档：os.waitpid](https://docs.python.org/zh-cn/3/library/os.html#os.waitpid)
- 问题：为什么父进程要 `waitpid`？子进程的退出状态怎么取出来？

```python
import os

pid = os.fork()
if pid == 0:
    os._exit(7)
else:
    _, status = os.waitpid(pid, 0)
    print(os.WIFEXITED(status), os.WEXITSTATUS(status))
```

- 答案：

```text
True 7
```

子进程结束后，它的退出状态不会凭空消失，而是由操作系统保留，直到父进程调用 `wait`/`waitpid` 来"收尸"取走这个信息（如果父进程一直不取，子进程会变成僵尸进程，见 Q07-18 之外的常见追问）。`WIFEXITED` 判断子进程是不是正常退出（而不是被信号杀死），`WEXITSTATUS` 从状态里取出退出码，这里是 `os._exit(7)` 传的 7。

### Q07-03 管道：父子进程通信

- 类型：代码题
- 出处：[Python 官方文档：os.pipe](https://docs.python.org/zh-cn/3/library/os.html#os.pipe)
- 问题：父子进程各自拥有独立内存，怎样互相传递数据？

```python
import os

r, w = os.pipe()
pid = os.fork()
if pid == 0:
    os.close(r)
    os.write(w, b"hello from child")
    os._exit(0)
else:
    os.close(w)
    print(os.read(r, 100))
    os.waitpid(pid, 0)
```

- 答案：

```text
b'hello from child'
```

管道是操作系统提供的一块特殊缓冲区，`pipe()` 返回一对文件描述符：`r` 只能读，`w` 只能写。`fork` 之后子进程也继承了这两个描述符，子进程往 `w` 写的数据，父进程能从 `r` 读到——这正是命令行里 `|` 管道操作符（主题 0 的 Q00-12）底层的实现机制。各自关掉用不到的一端是好习惯，能避免管道一直不关闭。

### Q07-04 进程各自独立的内存

- 类型：代码题
- 出处：[Python 官方文档：os.fork](https://docs.python.org/zh-cn/3/library/os.html#os.fork)（fork 复制整个进程的地址空间）
- 问题：子进程修改一个变量，父进程能看到这个修改吗？

```python
import os

x = [111]
pid = os.fork()
if pid == 0:
    x[0] = 222
    os._exit(0)
else:
    os.waitpid(pid, 0)
    print(x[0])
```

- 答案：

```text
111
```

`fork()` 会给子进程复制一份和父进程当时完全一样的内存（现代系统用"写时复制"技术优化，实际物理内存不会立刻真正复制，只有某一方要写入时才复制那一页，但逻辑上表现得就像各自独立），之后两个进程的内存互不影响。子进程改了自己那份 `x` 的拷贝，父进程的 `x` 仍然是 111。这和 Q07-12 线程共享内存形成直接对比。

### Q07-05 `getpid`/`getppid`

- 类型：代码题
- 出处：[Python 官方文档：os.getpid](https://docs.python.org/zh-cn/3/library/os.html#os.getpid)、[os.getppid](https://docs.python.org/zh-cn/3/library/os.html#os.getppid)
- 问题：子进程的父进程 id，和父进程自己的 id，是同一个数吗？

```python
import os
import sys

parent_pid = os.getpid()
pid = os.fork()
if pid == 0:
    print(os.getppid() == parent_pid)
    sys.stdout.flush()
    os._exit(0)
else:
    os.waitpid(pid, 0)
```

- 答案：

```text
True
```

每个进程都有一个唯一的 pid，以及一个指向"创建它的进程"的 ppid（父进程 id）。子进程通过 `os.getppid()` 查到的值，正好等于父进程通过 `os.getpid()` 查到的自己的 id——这就是"进程树"这个说法的由来：每个进程（除了最初的 1 号进程）都有一个父进程，形成一棵树状的层级结构。

### Q07-06 `exec` 替换进程映像

- 类型：代码题
- 出处：[Python 官方文档：os.execvp](https://docs.python.org/zh-cn/3/library/os.html#os.execvp)
- 问题：`exec` 和 `fork` 有什么本质区别？

```python
import os

r, w = os.pipe()
pid = os.fork()
if pid == 0:
    os.close(r)
    os.dup2(w, 1)  # 把标准输出重定向到管道
    os.execvp("echo", ["echo", "from-exec"])
    print("这行不会被执行")
else:
    os.close(w)
    print(os.read(r, 100))
    os.waitpid(pid, 0)
```

- 答案：

```text
b'from-exec\n'
```

`fork` 创建一个新进程（子进程是父进程的复制品）；`exec` 不创建新进程，而是**替换**当前进程的代码、数据，用一个全新的程序接管这个进程剩下的生命周期——`exec` 调用成功后，原来的代码（包括"这行不会被执行"那一句）不会再被执行，因为进程已经变成了 `echo` 程序。Shell 执行一条外部命令的典型做法正是"先 `fork` 出一个子进程，再在子进程里 `exec` 目标程序"，这也是为什么 Shell 本身不会因为运行了别的程序而消失。

### Q07-07 子进程继承环境变量

- 类型：代码题
- 出处：[Python 官方文档：os.environ](https://docs.python.org/zh-cn/3/library/os.html#os.environ)；与主题 0 的 Q00-25 相衔接
- 问题：父进程 `fork` 之前设置的环境变量，子进程能看到吗？

```python
import os
import sys

os.environ["MY_VAR"] = "hello"
pid = os.fork()
if pid == 0:
    print(os.environ.get("MY_VAR"))
    sys.stdout.flush()
    os._exit(0)
else:
    os.waitpid(pid, 0)
```

- 答案：

```text
hello
```

`fork` 复制父进程当时的整个状态，环境变量也在其中，所以子进程一创建出来就能看到父进程已经设置好的环境变量。但这个继承是"单向"的：子进程之后修改自己的环境变量，不会反过来影响父进程（原理和 Q07-04 内存隔离一致）。

### Q07-08 `mmap` 共享内存

- 类型：代码题
- 出处：[Python 官方文档：mmap 模块](https://docs.python.org/zh-cn/3/library/mmap.html)
- 问题：如果确实需要父子进程共享同一块内存（而不是各自独立），可以怎么做？

```python
import mmap
import os

buf = mmap.mmap(-1, 8)  # 匿名映射，默认在 Unix 上是 MAP_SHARED
buf[0:5] = b"hello"
pid = os.fork()
if pid == 0:
    buf[0:1] = b"H"
    os._exit(0)
else:
    os.waitpid(pid, 0)
    print(bytes(buf[0:5]))
```

- 答案：

```text
b'Hello'
```

普通的 Python 对象经过 `fork` 后各自独立（Q07-04），但 `mmap` 匿名映射的内存在 Unix 系统上默认是 `MAP_SHARED`：父子进程实际操作的是同一块物理内存，一方的修改另一方立刻可见。子进程把第一个字节改成大写 `H`，父进程读到的也是改过的结果。这是实现真正跨进程共享数据的常见手段之一，`multiprocessing.Value`、`multiprocessing.shared_memory` 底层都用到类似的机制。

### Q07-09 注册信号处理函数

- 类型：代码题
- 出处：[Python 官方文档：signal.signal](https://docs.python.org/zh-cn/3/library/signal.html#signal.signal)
- 问题：进程怎样"响应"一个信号，而不是被动接受默认行为？

```python
import signal
import os

received = []

def handler(signum, frame):
    received.append(signum)

signal.signal(signal.SIGUSR1, handler)
os.kill(os.getpid(), signal.SIGUSR1)
print(received == [signal.SIGUSR1])
```

- 答案：

```text
True
```

`signal.signal(信号, 处理函数)` 把某个信号绑定到一个自定义函数上，之后进程收到这个信号时会调用这个函数，而不是执行默认行为（默认行为往往是终止进程）。这里进程给自己发送了 `SIGUSR1`（用户自定义信号 1），处理函数被调用并记录下来。这也是很多程序"优雅关闭"的实现方式：捕获 `SIGTERM`，在真正退出前先做清理工作。

### Q07-10 `SIGTERM` 的默认行为是终止进程

- 类型：代码题
- 出处：[Python 官方文档：signal 模块](https://docs.python.org/zh-cn/3/library/signal.html)；与主题 0 的 Q00-32、主题 3 的 Q03-19 相衔接
- 问题：没有注册处理函数时，收到 `SIGTERM` 会怎样？

```python
import os
import signal
import time

pid = os.fork()
if pid == 0:
    time.sleep(10)
    os._exit(0)
else:
    os.kill(pid, signal.SIGTERM)
    _, status = os.waitpid(pid, 0)
    print(os.WIFSIGNALED(status), os.WTERMSIG(status))
```

- 答案：

```text
True 15
```

`SIGTERM`（编号 15）的默认行为是终止进程，`kill` 命令默认发送的就是这个信号。`os.WIFSIGNALED` 判断进程是不是被信号终止（而不是正常 `exit`），`os.WTERMSIG` 取出杀死它的信号编号。子进程原本要睡 10 秒，但被 `SIGTERM` 提前终止了，没等到睡完。这和主题 0 Q00-32、主题 3 Q03-19 里"被信号杀死时退出码是 128+信号编号"是同一套机制：这里我们看到的是原始的信号编号 15，Shell 层面看到的退出码则会是 128+15=143。

### Q07-11 正常退出与被信号终止是两回事

- 类型：代码题
- 出处：[Python 官方文档：os.WIFEXITED](https://docs.python.org/zh-cn/3/library/os.html#os.WIFEXITED)、[os.WIFSIGNALED](https://docs.python.org/zh-cn/3/library/os.html#os.WIFSIGNALED)
- 问题：`wait` 返回的状态，怎样区分子进程是自己 `return`/`exit` 结束的，还是被信号杀死的？

```python
import os
import signal

pid1 = os.fork()
if pid1 == 0:
    os._exit(3)
_, s1 = os.waitpid(pid1, 0)

pid2 = os.fork()
if pid2 == 0:
    os.kill(os.getpid(), signal.SIGKILL)
_, s2 = os.waitpid(pid2, 0)

print(os.WIFEXITED(s1), os.WIFSIGNALED(s2))
```

- 答案：

```text
True True
```

同一个 `wait` 状态，需要先判断"它是怎么结束的"再去解读具体数值：`WIFEXITED` 为真表示是正常退出（这时用 `WEXITSTATUS` 取退出码，如 Q07-02）；`WIFSIGNALED` 为真表示是被信号杀死（这时用 `WTERMSIG` 取信号编号，如 Q07-10）。两者是互斥的：一个进程要么正常退出，要么被信号终止，不会同时是这两种情况。

### Q07-12 线程共享内存

- 类型：代码题
- 出处：[Python 官方文档：threading 模块](https://docs.python.org/zh-cn/3/library/threading.html)；与 Q07-04 的进程隔离形成对比
- 问题：多个线程能不能直接读写同一个变量？

```python
import threading

counter = 0

def inc():
    global counter
    for _ in range(100000):
        counter += 1

threads = [threading.Thread(target=inc) for _ in range(4)]
for t in threads:
    t.start()
for t in threads:
    t.join()
print(counter)
```

- 答案：

```text
400000
```

线程和进程最根本的区别：同一进程内的所有线程共享同一份内存空间，不像 `fork` 出来的进程那样各自独立（对比 Q07-04）。这里 4 个线程操作的是同一个 `counter` 变量，都能看到彼此的修改。这个例子恰好得到了正确的结果 400000，但这**不代表**多线程操作共享变量总是安全的，见 Q07-13。

### Q07-13 竞态条件

- 类型：代码题
- 出处：竞态条件（race condition）的标准定义
- 问题：多个线程同时"读取、修改、写回"同一个变量，一定会得到预期的结果吗？

```python
import threading
import time

counter = [0]

def inc_unsafe():
    for _ in range(5):
        temp = counter[0]
        time.sleep(0.001)  # 故意制造机会，让别的线程有空插进来
        counter[0] = temp + 1

threads = [threading.Thread(target=inc_unsafe) for _ in range(4)]
for t in threads:
    t.start()
for t in threads:
    t.join()
print(counter[0], counter[0] == 4 * 5)
```

- 答案：

```text
5 False
```

"读取当前值、算出新值、写回"这三步不是一个不可分割的整体（不是"原子操作"）。如果一个线程刚读完 `counter[0]` 的旧值还没来得及写回，另一个线程也读到了同一个旧值，两个线程各自基于这个旧值算出的"新值"就会互相覆盖，其中一次加法效果凭空丢失了——这就是竞态条件。这里故意用 `sleep` 制造出"读完就被切换走"的时机，让每个线程的 5 次自增互相踩踏，最终结果远小于期望的 20。竞态条件的危险之处在于它不总是发生，运气好的时候（比如 Q07-12 那种没有刻意制造交错的场景）结果可能碰巧是对的，这让它在实际项目里格外难以发现和复现。

### Q07-14 用锁避免竞态

- 类型：代码题
- 出处：[Python 官方文档：threading.Lock](https://docs.python.org/zh-cn/3/library/threading.html#threading.Lock)
- 问题：给 Q07-13 的代码加上锁，结果会怎样？

```python
import threading
import time

counter = [0]
lock = threading.Lock()

def inc_safe():
    for _ in range(5):
        with lock:
            temp = counter[0]
            time.sleep(0.001)
            counter[0] = temp + 1

threads = [threading.Thread(target=inc_safe) for _ in range(4)]
for t in threads:
    t.start()
for t in threads:
    t.join()
print(counter[0] == 4 * 5)
```

- 答案：

```text
True
```

`Lock` 保证同一时刻只有一个线程能进入 `with lock:` 包起来的代码块，其他线程必须排队等待，直到持锁的线程释放锁。这样"读取、修改、写回"这几步就不会被别的线程插队打断，Q07-13 的问题就解决了。代价是失去了并发执行这段代码的能力——加锁的范围应该尽量小，只包住真正需要保护的部分。

### Q07-15 全局解释器锁（GIL）

- 类型：概念题
- 出处：[Python 官方术语表：全局解释器锁](https://docs.python.org/zh-cn/3/glossary.html#term-global-interpreter-lock)
- 问题：GIL 是什么？它对多线程程序有什么影响？
- 答案：

Python 官方术语表的定义：GIL 是 CPython 解释器采用的一种机制，"确保同一时刻只有一个线程在执行 Python 字节码"。它简化了 CPython 内部的实现（不用担心多个线程同时改动内置对象带来的内部数据结构损坏），但代价是牺牲了多核 CPU 上的真正并行能力——即使开了再多线程，同一时刻能执行 Python 代码的也只有一个。这也是为什么 Q07-12、Q07-13 的例子里"竞态条件"依然会发生：GIL 保证的是解释器内部数据结构不损坏，不代表你自己写的"读取、修改、写回"这类多步操作是原子的。

### Q07-16 计算密集型任务用多进程绕开 GIL

- 类型：代码题
- 出处：[Python 官方文档：multiprocessing 模块](https://docs.python.org/zh-cn/3/library/multiprocessing.html)
- 问题：GIL 限制了多线程的并行计算能力，那怎样才能真正利用多核 CPU？

```python
from multiprocessing import Process, Value

def inc(v):
    for _ in range(100000):
        with v.get_lock():
            v.value += 1

v = Value("i", 0)
procs = [Process(target=inc, args=(v,)) for _ in range(4)]
for p in procs:
    p.start()
for p in procs:
    p.join()
print(v.value)
```

- 答案：

```text
400000
```

`multiprocessing` 用真正独立的进程（而不是线程）来并行工作，每个进程有自己的 Python 解释器和自己的 GIL，互不干扰，因此能真正利用多核 CPU 做计算密集型任务。因为进程之间默认内存不共享（Q07-04），要共享一个计数器必须显式使用 `multiprocessing.Value` 这类专门设计的跨进程共享对象（内部通常基于 Q07-08 的共享内存机制），并且仍然需要加锁（`get_lock()`）来避免竞态——GIL 不存在了，但竞态条件的问题（Q07-13）并没有消失，只是换了一种需要处理的方式。

### Q07-17 I/O 操作会释放 GIL

- 类型：概念题
- 出处：[Python 官方术语表：全局解释器锁](https://docs.python.org/zh-cn/3/glossary.html#term-global-interpreter-lock)（"在执行 I/O 操作时也总是会释放 GIL"）
- 问题：如果任务大部分时间在等网络或等磁盘（而不是做纯计算），多线程还有意义吗？
- 答案：

有意义。官方术语表特别指出，"在执行 I/O 操作时也总是会释放 GIL"：一个线程发起网络请求或读写文件、进入等待状态时，会主动让出 GIL，让别的线程有机会执行 Python 代码。所以对于"大部分时间在等待外部资源"的任务（比如同时下载多个文件、同时处理多个网络连接），多线程仍然能带来明显的并发收益，即使无法像多进程那样利用多个 CPU 核心做纯计算。GIL 限制的核心是"CPU 密集型的纯 Python 计算"，不是所有多线程场景。

### Q07-18 死锁

- 类型：概念题
- 出处：死锁的标准定义（需要同时满足互斥、占有并等待、不可抢占、循环等待四个条件）
- 问题：死锁是怎么发生的？举一个最简单的例子。
- 答案：

死锁是指多个执行者（线程或进程）各自持有一部分资源，同时又在等待对方持有的资源，谁都无法继续往下执行，永远僵持。最简单的例子：线程 A 先锁住锁 1，再想去锁锁 2；线程 B 恰好相反，先锁住锁 2，再想去锁锁 1。如果 A 锁住 1 之后、B 锁住 2 之后，两者都还没来得及拿到第二把锁，就会永远互相等待。避免死锁常见的办法是：所有代码都按照同一个固定顺序去获取多把锁（比如永远先锁 1 后锁 2），从根本上消除"循环等待"这个条件。这道题不提供可运行的示例代码：真的复现死锁会让程序卡死，不适合自动化验证，但理解这个原理对判断"这段加锁代码会不会卡死"很重要。

### Q07-19 文件描述符是小整数

- 类型：代码题
- 出处：[Python 官方文档：os.pipe](https://docs.python.org/zh-cn/3/library/os.html#os.pipe)（文件描述符是操作系统分配的整数）
- 问题：新打开一个文件，操作系统会给它分配一个什么样的编号？0、1、2 为什么不会被分配到？

```python
import os

r, w = os.pipe()
print(r > 2, w > 2, r != w)
os.close(r)
os.close(w)
```

- 答案：

```text
True True True
```

操作系统用一个小整数（文件描述符）来标识一个进程打开的每一个文件、管道或网络连接。每个进程启动时，0、1、2 已经被预先分配给标准输入、标准输出、标准错误（这也是 Q03 里 `printf` 默认写到屏幕、`stderr` 单独重定向的底层依据），新打开的文件、管道会依次分配到 3 及以后还没被占用的数字。同一个进程内两次 `pipe()` 得到的描述符各不相同。

### Q07-20 虚拟内存：每个进程独立的地址空间

- 类型：代码题
- 出处：虚拟内存的基本模型（每个进程看到的地址空间由操作系统映射到物理内存）
- 问题：父子进程里，同一个 Python 对象的内存地址是一样的吗？

```python
import os
import sys

x = [1, 2, 3]
addr_before = id(x)
pid = os.fork()
if pid == 0:
    print(id(x) == addr_before)
    sys.stdout.flush()
    os._exit(0)
else:
    os.waitpid(pid, 0)
```

- 答案：

```text
True
```

`id(x)` 在 CPython 里返回的是对象的内存地址。子进程复制了父进程当时的整个地址空间（Q07-04），包括这个对象所在的那部分虚拟地址，所以从"虚拟地址"的角度看，两边的 `id(x)` 相同。但这只是各自地址空间里的"门牌号"，背后对应的物理内存已经是两份独立的（写时复制），子进程改了 `x` 的内容不会影响父进程（回到 Q07-04 的结论）。这正是虚拟内存的意义：每个进程都以为自己独占一整片地址空间，实际的物理内存分配和隔离由操作系统在背后处理。
